# Interactive Dither Studio — проектный бриф и спецификация

**Статус:** согласованный исходный контекст для старта нового проекта  
**Дата:** 4 сентября 2026  
**Рабочее название:** Interactive Dither Studio  
**Назначение документа:** передать в новый проект полный контекст, чтобы команда или агент могли спроектировать и реализовать приложение без повторного восстановления исходной задачи.

---

## 1. Коротко о продукте

Нужно создать локальное визуальное веб-приложение, которое связывает дизайнера и разработчика. Дизайнер загружает изображение или видео, настраивает дизеринг, цвет, анимацию, реакцию на курсор и локальные пульсирующие акценты, видит реальный интерактивный результат и получает ровно три основных варианта экспорта:

- PNG — статичный кадр и fallback;
- MP4 — неинтерактивная демонстрация настроенной анимации;
- JSON — полная конфигурация сцены для воспроизведения интерактивного эффекта в общем runtime-компоненте.

Главный результат — не видео с имитацией эффекта, а воспроизводимая интерактивная сцена. Один и тот же рендерер должен использоваться внутри редактора и на конечном сайте. При одинаковом исходнике и JSON-конфигурации результат должен совпадать.

---

## 2. Контекст возникновения задачи

Для страницы Human.md была создана визуальная концепция Hero-секции:

- слева находится механическая рука агента;
- справа — человеческая рука;
- между ними расположен оранжевый объект, символизирующий запрос на решение;
- изображение переведено в точечный дизеринг;
- поверх иллюстрации расположены HTML-бабблы диалога агента и человека;
- центральный объект должен пульсировать;
- частицы должны слегка мерцать и реагировать на курсор.

Исходное изображение было создано отдельно генеративным инструментом, после чего стилистика была получена через внешний редактор Tooooools. Концепция одобрена, поэтому теперь требуется не только статичный макет, но и контролируемый способ получения такого эффекта для разработки.

Дизайнер хочет самостоятельно управлять результатом и передавать разработчику практически готовую сцену, а не словесное описание анимации.

---

## 3. Проблема

Сейчас процесс разорван:

1. Дизайнер создаёт или генерирует исходное изображение.
2. Внешний сервис превращает его в статичный дизеринг.
3. В Figma собирается композиция.
4. Разработчик должен заново интерпретировать эффект, движение и интерактивность.

Из-за этого дизайнер не контролирует финальную реализацию, а разработчик вынужден вручную угадывать параметры. Новый инструмент должен превратить визуальный эффект в формальную, воспроизводимую конфигурацию.

---

## 4. Основной продуктовый принцип

> Editor preview equals production output.

Перевод: предпросмотр в редакторе равен результату в продакшене.

Нельзя создавать отдельную упрощённую логику для редактора и другую для сайта. Обе части должны использовать общий модуль рендеринга. В противном случае JSON перестанет быть надёжным контрактом между дизайнером и разработчиком.

Дополнительные принципы:

1. **Configuration over imitation.** Дизайнер передаёт не ролик с примером, а параметры сцены.
2. **Deterministic output.** Одинаковые исходник, seed и JSON дают одинаковый результат.
3. **Non-destructive editing.** Настройки не изменяют оригинальный файл.
4. **Local-first.** В первой версии обработка выполняется в браузере без обязательного сервера и загрузки пользовательских файлов в облако.
5. **Progressive complexity.** Сначала один качественный движок дизеринга и понятная интерактивность; дополнительные эффекты добавляются позднее.

## 5. Референсы и роль каждого из них

### 5.1. Tooooools — Dithering

URL: <https://www.tooooools.app/effects/dithering>

Использовать как функциональный и визуальный референс для:

- загрузки JPG, PNG и MP4;
- быстрого живого предпросмотра;
- изменения размера холста;
- предварительной обработки изображения;
- выбора алгоритма дизеринга;
- управления размером пикселя, порогом и цветовым режимом;
- экспорта статичного результата.

Подтверждённые элементы управления на странице:

- Canvas Size;
- Blur;
- Grain;
- Gamma;
- Black Point;
- White Point;
- Show Effect;
- Pattern: F-S, Bayer, Random;
- Pixel Size;
- Color Mode;
- Threshold;
- Export Canvas.

Не копировать исходный код, интерфейс, брендинг или уникальные ассеты Tooooools. Нужно реализовать собственный интерфейс и собственную обработку на базе общеизвестных алгоритмов. Под «reverse engineering» в этом документе понимается анализ поведения и набора параметров, а не копирование закрытой реализации.

### 5.2. Human.md demo

URL: <https://www.gethuman.md/sapien.html>

Использовать как технический референс для интерактивной Canvas-сцены:

- изображение переводится в сетку частиц;
- используется ordered dithering Bayer 8×8;
- светлые участки слегка мерцают;
- сцена имеет медленное «дыхание»;
- курсор создаёт слабое локальное влияние;
- между пальцами расположен цветной пульсирующий акцент;
- акцент использует двойной ритм;
- рендер ограничен 30 кадрами в секунду;
- анимация останавливается вне viewport;
- device pixel ratio ограничен значением 2;
- при prefers-reduced-motion показывается статичное состояние;
- Canvas имеет role="img" и осмысленный aria-label.

Проверенные параметры демо, полезные как отправная точка:

- Bayer matrix: 8×8;
- desktop cell size: 4 CSS px;
- mobile cell size: 3 CSS px;
- frame rate: 30 fps;
- pulse cycle: 3600 ms;
- double pulse: сильный первый и более мягкий второй импульс;
- pointer influence radius: около 15% ширины сетки;
- анимация запускается через IntersectionObserver только при видимости Canvas.

### 5.3. Figma-концепция Human.md

URL: <https://www.figma.com/design/iylx1T9ZuYkodD0dTXFwqj/Human.md?node-id=9-482>

Использовать как арт-дирекшн и проверку композиции:

- чёрный фон;
- монохромные руки;
- яркий оранжевый объект между ними;
- точечное растворение изображения по краям;
- HTML-бабблы над иллюстрацией;
- семантическая последовательность: `agent → decision request → human`.

### 5.4. Важное расхождение референсов

На предоставленном скриншоте Tooooools визуально выбран алгоритм **Floyd–Steinberg (F-S)**, а подпись в Figma-концепции содержит слово **Bayer**. Это не одно и то же.

Требование:

- поддержать оба алгоритма;
- создать сравнение на одном исходном изображении;
- выбрать финальный алгоритм по визуальному соответствию утверждённому Hero;
- после выбора исправить подпись в макете, если она не соответствует реальному алгоритму.

Не считать Bayer автоматически утверждённым вариантом только из-за подписи в макете.

## 6. Целевая аудитория

### Основной пользователь

Визуальный или продуктовый дизайнер, который:

- не обязан понимать Canvas, WebGL и код анимации;
- хочет управлять эффектом визуально;
- должен видеть реакцию сцены в реальном времени;
- передаёт разработчику точную конфигурацию.

### Вторичный пользователь

Frontend-разработчик, который:

- подключает общий runtime-компонент;
- получает исходный ассет и JSON;
- не восстанавливает параметры вручную;
- может валидировать конфигурацию и воспроизвести сцену локально.

## 7. Основной пользовательский сценарий

1. Пользователь создаёт новый проект сцены.
2. Загружает JPG, PNG или MP4.
3. Настраивает размер, кадрирование и фон.
4. Регулирует предварительную обработку изображения.
5. Выбирает алгоритм дизеринга и настраивает его.
6. Настраивает палитру.
7. Включает и регулирует постоянное движение частиц.
8. Включает реакцию на курсор и тестирует её прямо в preview.
9. Ставит pin в нужной области изображения.
10. Настраивает цвет, радиус и ритм пульсации pin.
11. Проверяет desktop, tablet, mobile и reduced-motion состояния.
12. Отдельно экспортирует PNG, MP4 и JSON.
13. Передаёт разработчику эти три файла.
14. Разработчик подключает общий renderer и передаёт ему экспортированный JSON и PNG-ассет.

## 9. Функциональные требования

## 9.1. Проекты и источник

Приложение должно:

- создавать пустой проект;
- импортировать локальный JPG или PNG в первой фазе;
- импортировать MP4 в отдельной видео-фазе;
- сохранять оригинальный файл неизменным;
- хранить имя, размеры, формат и соотношение сторон источника;
- показывать ошибку для повреждённого или неподдерживаемого файла;
- предупреждать о слишком большом файле;
- сохранять проект и конфигурацию локально;
- импортировать ранее экспортированный JSON.

SVG не входит в первичный scope: сначала его необходимо растрировать.

## 9.2. Canvas и композиция

Настройки:

- ширина и высота экспортного Canvas;
- готовые aspect ratio: Original, 1:1, 4:3, 16:9, 9:16, Custom;
- fit: contain, cover, fill;
- масштаб;
- смещение по X и Y;
- поворот при необходимости;
- цвет или прозрачность фона;
- безопасная область;
- независимый экспорт в 1× и 2×.

Preview-размер не должен определять реальное экспортное разрешение.

## 9.3. Предварительная обработка

Обязательные параметры:

| Параметр | Начальный диапазон | Стартовое значение | Назначение |
|---|---:|---:|---|
| Blur | 0–20 px | 0 | Смягчает детали перед дизерингом |
| Grain | 0–1 | 0.07 | Добавляет контролируемый шум |
| Gamma | 0.1–4 | 2 | Перераспределяет средние тона |
| Black Point | 0–254 | 0 | Определяет нижнюю границу яркости |
| White Point | 1–255 | 251 | Определяет верхнюю границу яркости |

Правила:

- White Point всегда должен быть больше Black Point;
- зерно должно иметь фиксируемый seed;
- изменения должны отображаться без подтверждения;
- должен быть Reset section;
- вычислительно дорогие операции допускается применять с debounce, но preview должен ощущаться живым.

Brightness и Contrast можно добавить позднее, если они действительно необходимы после тестирования Gamma и точек белого/чёрного.

## 9.4. Дизеринг

Обязательные алгоритмы:

1. Floyd–Steinberg error diffusion;
2. Bayer ordered dithering;
3. Random threshold dithering.

Обязательные параметры:

| Параметр | Начальный диапазон | Стартовое значение |
|---|---:|---:|
| Pixel Size | 1–24 CSS px | 2 |
| Threshold | 0–255 | 255 |
| Algorithm | enum | floyd-steinberg |
| Effect Enabled | boolean | true |
| Color Mode | boolean | false |
| Random Seed | integer | 1 |

Для Bayer поддержать как минимум матрицу 8×8. Возможность 2×2 и 4×4 допустима позднее.

Алгоритм и все случайные значения должны быть детерминированы конфигурацией.

## 9.5. Палитра

Минимальная модель содержит:

- background;
- faint dots;
- dim dots;
- bright dots;
- shimmer color;
- accent color для каждого pin.

Нужны:

- color picker;
- ручной ввод обычного шестизначного HEX-кода из Figma, например `#FF5C30`;
- сохранение собственных палитр;
- монохромный режим;
- инверсия светлого и тёмного как дополнительная настройка.

Правила HEX-ввода:

- основная форма в интерфейсе — `#` и шесть символов, например `#FF5C30`;
- разрешены цифры `0–9` и буквы `A–F` без учёта регистра;
- при вставке `FF5C30` приложение автоматически добавляет `#`;
- трёхзначный сокращённый HEX и alpha-канал в восьмизначном HEX не входят в MVP;
- неверное значение не применяется и сопровождается понятной ошибкой;
- отдельный HEX задаётся для фонового мерцания и для каждого акцентного pin;
- значение из поля, color picker и JSON всегда синхронизировано.

## 9.6. Постоянное движение

Нужно поддержать два независимых эффекта.

### Shimmer

Мягкое изменение яркости отдельных частиц.

Параметры:

- enabled;
- color: шестизначный HEX-код, независимо от цвета акцентного pin;
- amount: 0–0.5;
- speed: 0–2;
- spatial scale: крупное или мелкое поле;
- seed;
- affects: all, highlights only, custom threshold.

### Breathing

Медленное общее изменение яркости или масштаба светлых участков.

Параметры:

- enabled;
- amount: 0–0.2;
- duration: 500–10000 ms;
- easing: linear, ease-in-out, sine.

Стартовый арт-дирекшн для Human.md:

- движение спокойное;
- изображение ощущается живым, но не дрожит;
- текст Hero остаётся главным элементом;
- ориентир длительности дыхания: 4–6 секунд.

## 9.7. Реакция на курсор

MVP-режим: **Highlight** — частицы около курсора становятся немного ярче и/или крупнее.

Параметры:

- enabled;
- radius: 0.01–0.5 ширины сцены;
- strength: 0–1;
- falloff: linear, smooth, gaussian;
- decay: 0.8–0.999;
- brightness boost;
- size boost;
- optional interaction color;
- disabled on touch или touch-follow mode.

Стартовый арт-дирекшн:

- радиус около 12–15% ширины сцены;
- эффект слабый;
- частицы не должны сильно разлетаться;
- после ухода курсора влияние исчезает примерно за 0.6–1 секунду.

Displacement, repulsion и particle scattering можно добавить после MVP. Для утверждённой сцены они не обязательны.

## 9.8. Pin — локальный акцент

Pin — точка, закреплённая за конкретной областью сцены. Она должна влиять на частицы внутри радиуса, а не быть обычным нарисованным поверх кругом.

Размещение:

- пользователь включает режим Add Pin;
- кликает по preview;
- координаты сохраняются в нормализованном виде от 0 до 1;
- pin сохраняет положение при изменении размеров Canvas;
- pin можно перемещать мышью или вводить X/Y численно;
- интерфейс показывает координаты дизайнеру как проценты `X: 0–100%` и `Y: 0–100%`;
- JSON хранит те же координаты как числа `0–1`;
- изменение координат численно немедленно перемещает pin в preview;
- после выбора pin его центр обозначается точным маркером, который не попадает в экспорт.

Параметры pin:

- id и name;
- enabled;
- normalized X/Y;
- color: отдельный шестизначный HEX-код из Figma;
- core radius;
- bloom radius;
- softness;
- intensity;
- blend mode;
- pulse enabled;
- pulse type: single, double, continuous;
- cycle duration;
- minimum/maximum intensity;
- minimum/maximum radius;
- phase delay;
- два пользовательских пика для double pulse.

Стартовый арт-дирекшн для Human.md:

- pin расположен в центре оранжевой сферы;
- влияет на уже существующие частицы;
- цвет: около `#FF5C30`;
- цикл: около 3600 ms;
- сначала сильный импульс, затем более мягкий второй;
- после двойного импульса следует пауза;
- цвет не должен заметно окрашивать руки за пределами bloom radius.

MVP должен поддерживать несколько pin, даже если первая сцена использует один. Все pin используют одну модель данных.

Ограничение MVP: pin привязан к координатам сцены, а не автоматически отслеживает объект внутри видео. Object tracking и animated masks являются отдельной будущей задачей.

## 9.9. Работа с видео

Целевой продукт должен принимать MP4, как референс Tooooools, и применять обработку к видеокадрам.

Требования видео-фазы:

- play, pause, loop;
- mute by default;
- выбор poster frame;
- обработка текущего кадра тем же pipeline;
- сохранение постоянных pin в координатах Canvas;
- MP4-экспорт обработанного preview;
- статичный fallback из выбранного кадра.

Видео не должно блокировать выпуск image-MVP. Сначала необходимо доказать качество и воспроизводимость эффекта на JPG/PNG.

## 9.10. Responsive-настройки

Минимум три preview-режима:

- desktop;
- tablet;
- mobile.

Настройки должны делиться на:

- общие параметры сцены;
- breakpoint overrides.

Возможные overrides:

- pixel size;
- crop/position;
- pointer enabled;
- pin radius;
- animation amount;
- export aspect ratio.

Координаты pin остаются нормализованными. Если mobile использует другое кадрирование, разрешается отдельная позиция pin для breakpoint.

## 9.11. Доступность и производительность

Обязательно:

- поле для aria-label сцены;
- статичный fallback image;
- поддержка prefers-reduced-motion;
- Play/Pause в редакторе;
- возможность отключить pointer interaction;
- ограничение frame rate;
- пауза анимации вне viewport;
- пауза при скрытой вкладке;
- device pixel ratio cap по умолчанию 2;
- отсутствие обязательных сетевых запросов во время рендера;
- предварительная обработка исходника один раз при изменении параметров, а не каждый animation frame.

Стартовое значение runtime frame rate: 30 fps. 60 fps допускается как пользовательская опция, но не как обязательный режим.

## 11. Экспорт

## 11.1. PNG

PNG — единственный статичный формат экспорта. JPEG и WebP намеренно не поддерживаются, чтобы не создавать лишнюю опциональность.

Требования:

- lossless-экспорт;
- поддержка прозрачного или заданного фона;
- 1× и 2×;
- пользовательские width/height;
- текущий кадр или заданный poster frame;
- возможность выбрать спокойное reduced-motion состояние;
- production resolution не зависит от фактического CSS-размера preview.

PNG должен быть пригоден одновременно как статичный референс, fallback и передаваемый вместе с JSON ассет сцены.

## 11.2. Конфигурация

Основной файл передачи разработчику: `scene.json`.

Требования:

- валидный JSON без комментариев;
- `schemaVersion`;
- `rendererVersion`;
- все визуальные параметры;
- seed для каждого случайного процесса;
- нормализованные координаты;
- ссылки на ассеты относительными путями;
- отсутствие локальных `blob:` URL;
- возможность повторного импорта в редактор;
- миграция старых schemaVersion в будущих версиях.

## 11.3. Комплект передачи разработчику

Приложение предоставляет три отдельные команды экспорта: `Export PNG`, `Export MP4` и `Export configuration`. При передаче разработчику файлы складываются рядом:

```text
human-hero-dither/
├── human-hero.png
├── human-hero.mp4
└── human-hero.json
```

Общий renderer и документация по его подключению принадлежат самому проекту приложения и не считаются дополнительными форматами экспорта.

## 11.4. MP4

MP4 — единственный видеоформат экспорта. WebM и GIF намеренно не поддерживаются.

Требования:

- экспорт фонового мерцания и анимации pin;
- выбранные width, height, frame rate и duration;
- бесшовный loop, если сцена настроена как циклическая;
- MP4 является визуальной демонстрацией и не содержит настоящей реакции на курсор;
- JSON остаётся источником истины для интерактивного поведения на сайте.

## 13. Техническая архитектура

Рекомендуется один репозиторий с отдельными пакетами:

```text
apps/
└── editor/             # визуальное приложение дизайнера
packages/
├── renderer-core/      # Canvas-движок без зависимости от интерфейса
├── scene-schema/       # типы, validation, migration JSON
└── react/              # React-обёртка для продуктовых сайтов
```

### Renderer Core

Отвечает только за:

- декодирование подготовленного media source;
- preprocessing;
- построение intensity map;
- дизеринг;
- particle batches;
- motion state;
- pointer field;
- pin fields;
- отрисовку кадра;
- resize и lifecycle.

Renderer не должен знать о слайдерах, панелях или файловом интерфейсе редактора.

### Scene Schema

Отвечает за:

- TypeScript-типы;
- runtime-validation JSON;
- default values;
- ограничения диапазонов;
- migration между версиями;
- человекочитаемые ошибки.

### Editor

Отвечает за:

- интерфейс;
- загрузку файлов;
- историю изменений;
- presets;
- live-preview через renderer-core;
- импорт и экспорт;
- локальное сохранение проектов.

### React Wrapper

Предоставляет разработчику минимальный интерфейс подключения сцены на сайт и управляет:

- mount/unmount;
- ResizeObserver;
- IntersectionObserver;
- prefers-reduced-motion;
- visibility lifecycle;
- aria-label и fallback.

### Canvas 2D или WebGL

Для MVP использовать Canvas 2D, потому что подтверждённое Human.md demo уже доказывает достаточность этого подхода для нужного визуала.

Переходить на WebGL только если профилирование покажет, что:

- требуемое количество частиц не держит целевые 30 fps;
- видеообработка слишком тяжёлая;
- нужны сложные displacement-эффекты.

Не усложнять первую версию shader-архитектурой без доказанной необходимости.

## 14. Data flow

```text
Local media
  → decode
  → crop / resize
  → blur / grain / gamma / black-white mapping
  → luminance or color intensity map
  → selected dither algorithm
  → base particle field
  → ambient motion
  → pointer field
  → pin fields
  → Canvas frame
  → preview / static export / motion capture
```

Preprocessing и базовый particle field пересчитываются только при изменении зависимых настроек, источника или размера сетки. Каждый animation frame должен применять только динамические слои.

---

## 15. Интеграция на продуктовый сайт

Основной вариант:

1. Команда один раз подключает общий renderer package.
2. Дизайнер экспортирует `scene.json` и ассеты.
3. Разработчик кладёт ассеты в проект.
4. React-компонент получает `scene.json`.
5. Бабблы, кнопки и текст Hero остаются обычными HTML-элементами поверх Canvas.

Почему бабблы нельзя запекать в Canvas:

- текст станет менее доступным;
- ухудшится responsive;
- усложнится локализация;
- разработчик не сможет нормально управлять состояниями;
- текст может потерять резкость.

Canvas отвечает только за художественную сцену и её интерактивность.

## 16. Состояния и ошибки

Нужно предусмотреть:

- empty state до загрузки;
- drag-and-drop highlight;
- unsupported format;
- corrupted media;
- file too large;
- invalid JSON;
- unsupported schemaVersion;
- missing source asset;
- blackPoint >= whitePoint;
- export failure;
- video codec unavailable;
- performance warning;
- lost file reference после перезагрузки;
- восстановление последней локальной конфигурации.

Любая ошибка должна объяснять дизайнеру, что произошло и как исправить ситуацию, без внутренних технических терминов.

## 19. Критерии готовности Image MVP

MVP считается готовым, если:

1. Дизайнер загружает исходное изображение Human.md.
2. Может воспроизвести утверждённый статичный дизеринг достаточно близко к Figma-референсу.
3. Может сравнить Floyd–Steinberg и Bayer на одном исходнике.
4. Может настроить спокойное мерцание без изменения кода.
5. Может вставить HEX-код цвета из Figma и получить тот же цвет мерцания или pin.
6. Может поставить pin кликом либо точным вводом координат X/Y.
7. Может протестировать реальную реакцию на курсор.
8. Может поставить pin в центр сферы и настроить двойной пульс.
9. Pin сохраняет положение при resize.
10. Preview и production renderer визуально совпадают.
11. Экспортированный JSON можно повторно импортировать без потери параметров.
12. Другой разработчик может подключить JSON и PNG по документации общего renderer без устного объяснения.
13. PNG имеет выбранное разрешение и ожидаемую композицию.
14. MP4 воспроизводит настроенное мерцание и пульсацию с выбранными длительностью и frame rate.
15. Экспорт ограничен тремя вариантами: PNG, MP4 и JSON.
16. Reduced-motion показывает корректный статичный кадр.
17. Анимация останавливается вне viewport.
18. Сцена стабильно поддерживает целевые 30 fps на согласованном тестовом устройстве.

## 20. Проверка качества

### Visual parity

- один исходник обрабатывается в Tooooools и новом редакторе;
- выставляются соответствующие параметры;
- результаты сравниваются side-by-side;
- проверяется плотность точек, края, средние тона и читаемость объектов;
- допускается собственная математическая реализация, но визуальный характер должен совпадать.

### Determinism

- экспортировать JSON;
- закрыть проект;
- импортировать JSON и тот же source;
- получить тот же кадр;
- повторить в другом браузере;
- проверить Random и Grain с сохранёнными seed.

### Responsive

- desktop, tablet, mobile;
- resize без скачка pin;
- сохранение aspect ratio;
- проверка отдельного mobile crop;
- touch-поведение.

### Performance

- 30 fps во время обычного preview;
- отсутствие рендера вне viewport;
- отсутствие повторного декодирования source каждый кадр;
- DPR cap работает;
- память освобождается после замены source.

### Accessibility

- aria-label доступен screen reader;
- reduced motion работает;
- fallback отображается без Canvas;
- UI editor доступен с клавиатуры;
- слайдеры имеют текстовые названия и числовой ввод.

## 21. Решения, принятые по умолчанию

Чтобы новый проект мог стартовать без дополнительных вопросов, принять следующие допущения:

- приложение — desktop-first локальный веб-редактор;
- стек интерфейса может быть React + TypeScript без жёсткой фиксации версий;
- основной renderer — Canvas 2D;
- один renderer используется и в editor, и в runtime;
- исходные файлы не отправляются на сервер;
- source of truth — versioned JSON;
- Phase 1 работает с JPG/PNG;
- MP4 export входит в основной MVP;
- MP4 input реализуется после стабильного image pipeline;
- несколько pin поддерживаются моделью с первого дня;
- объектный трекинг не входит в MVP;
- HTML-контент не рисуется в Canvas;
- visual parity важнее внутреннего совпадения с кодом Tooooools;
- production-анимация воспроизводится кодом из JSON, а MP4 служит переносимым визуальным результатом и референсом.

## 23. Материалы, которые нужно перенести в новый проект

MD-файл фиксирует продуктовую и техническую логику, но не может полностью заменить визуальные референсы. Вместе с ним рекомендуется положить в новый проект:

3. Скрин Tooooools, на котором одновременно видны полученный эффект и значения настроек.
4. Этот MD-файл.

Дополнительно полезно, но не обязательно:

- короткая запись реакции сцены Human.md на курсор и пульсации;
- ссылка на живое демо Human.md;
- ссылка на Figma-файл.

- текстовая спецификация не передаёт точную плотность и характер частиц;

- в новом чате может отсутствовать доступ к Figma;
- визуальное сравнение необходимо для проверки parity.
